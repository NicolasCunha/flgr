# Roadmap & Session Handoff

## Purpose

This file exists so a fresh agent session (or a human) can pick up work on flgr without re-deriving context from scratch. It is **not** a substitute for `git log` (authoritative for what changed) or the docs under `docs/business/requirements` and `docs/architecture/adr` (authoritative for what was decided and why). It captures the one thing those sources don't: *where the project stands right now, in what order the remaining work is meant to happen, and what's mid-discussion but not yet decided.*

**Update this file at the end of a work session** if the Current State, Build Order, or Open Decisions changed. Keep entries short — this is a map, not a diary.

## How to use this file

1. Read [Current State](#current-state) to know what's actually implemented vs. only documented.
2. Read [Open Decisions](#open-decisions--in-flight-discussions) before touching an area listed there — there may be an unresolved design conversation you'd otherwise redo or contradict.
3. Use [Suggested Build Order](#suggested-build-order) as a default sequence, not a hard rule — deviate if the user asks for something else.
4. Follow [workflow.md](workflow.md) for the actual step-by-step process on a task, and [documentation.md](documentation.md) for when docs need updating and when that needs the user's confirmation first.

### Users & Auth (Phase 1) — backend implemented 2026-08-17, no management UI

Requirement [0002](../docs/business/requirements/0002-user-management.md) + [ADR-0006](../docs/architecture/adr/0006-authentication-and-session-strategy.md), fully wired end to end (`internal/model`, `internal/repository`, `internal/service`, `internal/api/middleware`, `internal/api/handler`, `internal/api/router.go`) and smoke-tested against a running server. 99.0% backend test coverage, `golangci-lint` clean.

- **Auth**: `POST /api/v1/login` (bcrypt password check, sliding 30-min session cookie, 5-attempts/15-min lockout per ADR-0006), `POST /api/v1/logout`, `GET /api/v1/me`. Session token is opaque + SHA-256-hashed at rest, matching ADR-0006's reasoning for Service Key secrets.
- **Users CRUD**: `POST/GET /api/v1/users`, `GET/PATCH/DELETE /api/v1/users/:id` (`DELETE` soft-deletes per ADR-0005). Self-service edit of one's own name/email/password works without any permission; a user cannot change their own `status`.
- **Authorization gap closed 2026-08-17** (Phase 2 landed): every route below is now gated by the real permission it requires — see the Profiles & Permissions section below.
- **First-run setup wizard**: `GET /api/v1/setup` reports whether any User exists yet (`UserService.SetupNeeded`); `POST /api/v1/setup` creates exactly one User with no authenticated actor while none exists (`UserService.CompleteSetup`), 409s afterward, then assigns the new admin the seeded Administrador profile (`model.AdministradorProfileID`) via `SetupHandler.Complete` — without that assignment the wizard would produce a User with zero permissions, unable to do anything. Both routes are public/unauthenticated by necessity — nobody can be logged in yet on a fresh install. Same check-then-act race caveat as the email-uniqueness pre-check in `Create` (see the doc comment) — acceptable for a one-operator bootstrap moment.
- **Not built yet**: any frontend for user *management* — `src/features/auth/` only has `LoginPage.tsx`. No screen lists users, creates one, edits another user's name/email/status, or lets an admin assign Profiles/direct Permissions (`GET/PATCH /users/:id/profiles`, `/users/:id/permissions/direct` — see Phase 2 below) through the UI. Only self-service (via a future "my profile" page, also not built) and the setup wizard's one-time admin creation are reachable from the browser today; managing any *other* user requires calling the API directly. Flagged 2026-08-20 — this had been true since Phase 2 landed but wasn't previously called out in Suggested Build Order.

### Profiles & Permissions / RBAC (Phase 2) — backend implemented 2026-08-17, no management UI

Requirement [0003](../docs/business/requirements/0003-profile-and-permission-management.md), fully wired end to end and verified with a real running server (setup → login as admin → create an unprivileged user → confirm they're 403'd on admin actions but can still self-service → grant them a profile + a direct permission → confirm the Administrador-removal guard). 98.3% total backend coverage, `golangci-lint` clean.

- **Effective-permission resolution**: `AuthzService.HasPermission`/`.EffectivePermissions` (`internal/repository/authz_repository.go` does the union-of-direct-grants-and-all-profiles SQL query in one round trip; `AuthzService` applies the CRUD-implies-View rule in Go). Nothing is cached — re-evaluated fresh on every call, per ADR-0006's "permissions must be re-evaluated from current state on every request."
- **Profiles CRUD**: `POST/GET /api/v1/profiles`, `GET/PATCH/DELETE /api/v1/profiles/:id`, `GET /api/v1/profiles/:id/permissions`. Real hard delete (profiles carry no `created_by`/`modified_by` references from other tables, unlike Users — see ADR-0005). Editing permissions on the seeded system profile (Administrador) is rejected (`ProfileService.Update`); deleting it is rejected unless another profile independently holds the full permission catalog (`ProfileService.Delete` / `anotherProfileHoldsFullCatalog`) — both per 0003's ACs precisely.
- **Permission catalog**: `GET /api/v1/permissions` — read-only, any authenticated user (needed to render any permission-picker UI later).
- **User RBAC sub-resources** (`internal/service/user_access_service.go`, split out from `UserService` to avoid growing its dependency list): `GET/PATCH /api/v1/users/:id/profiles`, `GET/PATCH /api/v1/users/:id/permissions/direct`. All four require `User: Edit` — no self-service exception here (unlike name/email/password), since that would be a privilege-escalation hole.
- **How routes are gated** — two patterns, deliberately different:
  - No "self" concept (`POST/GET /users`, `DELETE /users/:id`, all of `/profiles/*`, all of `/users/:id/profiles` and `/users/:id/permissions/direct`): a static `middleware.RequirePermission(authzService, resource, action)` on the route in `router.go`.
  - Has a "self" concept (`GET/PATCH /users/:id`): the self-or-permission branch lives inside `UserService.Get`/`.Update` itself, since routing can't express "allow if self, else check a permission" as a static per-route rule. `UserService` takes a `PermissionChecker` interface (satisfied by `*AuthzService`) for exactly this.
  - `DELETE /users/:id` (deactivate) needed care: it's gated by `User: Remove` at the route, but internally calls the same field-mutation code `Update` uses — so that mutation logic was factored into an unexported `applyUpdate` that neither method's caller re-checks the *other* method's permission by accident.
- Not built yet: any frontend UI for Profiles/Permissions (no screens, just the backend API) — flag this if asked about RBAC "being done."

### Environments (Phase 3) — implemented 2026-08-17

Requirement [0001](../docs/business/requirements/0001-environment-management.md), fully wired end to end and verified with a real running server (seeded categories → create with an existing category → create with a brand-new "Other" category → rename + move category → duplicate-name rejection → delete). 98.1% total backend coverage, `golangci-lint` clean.

- **Environments CRUD**: `POST/GET /api/v1/environments`, `GET/PATCH/DELETE /api/v1/environments/:id`, gated by `Environment: Create/Edit/Remove/View` via route middleware (no "self" concept, same pattern as Profiles).
- **Category resolution**: `CreateEnvironmentInput`/`UpdateEnvironmentInput` take a `category_name` **string**, not an id — `EnvironmentService.resolveCategory` looks it up by name, or creates a new non-system category on the fly if it doesn't exist yet, per 0001's Content ("When the user picks 'Other'... that name is added to the list of selectable categories"). Handles the create-race (two requests picking the same brand-new name) by refetching on a unique-constraint conflict rather than just erroring.
- **`GET /api/v1/environment-categories`**: read-only, gated by `Environment: View` (0003's permission catalog has no separate category permission).
- **Not implemented — a real scope trim, not an oversight**: no HTTP endpoint to edit or delete a category directly. 0001's ACs ("the three seeded categories cannot be edited or removed," "a custom category cannot be removed while referenced") describe protective *rules*, but the Content section only ever describes categories being created as a side effect of creating/editing an environment — no direct category-management action is described, and 0003's permission catalog has no permission for one. If a future requirement wants direct category management, `EnvironmentCategoryRepository` would need a `Delete` method added (deliberately left off for now, matching "don't build for hypothetical future requirements").

### Service Keys (Phase 4) — implemented 2026-08-17

Requirement [0004](../docs/business/requirements/0004-service-key-management.md), fully wired end to end and verified with a real running server (create with an existing environment → secret shown once, never again on Get/List → rejected with no can_read/can_write → rejected with no environments → rejected with an unknown environment id → rename + flip can_write + Update → rejected clearing both can_read/can_write → rejected clearing environment_ids to empty → deactivate → confirm status Inactive → 403 for an unprivileged user). 98.1% total backend coverage, `golangci-lint` clean.

- **Service Keys CRUD**: `POST/GET /api/v1/service-keys`, `GET/PATCH/DELETE /api/v1/service-keys/:id`, gated by `ServiceKey: Create/Edit/Remove/View` via route middleware (no "self" concept, same pattern as Environments). `DELETE` deactivates (`status = Inactive`) rather than hard-deleting — service_keys rows are referenced by `created_by_service_key_id`/`modified_by_service_key_id` audit columns across the whole schema, so unlike Environments/Profiles this can never be a real delete, per [ADR-0005](../docs/architecture/adr/0005-audit-columns-and-soft-delete-convention.md)'s history-dependency rule.
- **Secret handling**: the plaintext secret is generated with the same `generateToken`/`hashToken` seam Sessions already use (SHA-256, not bcrypt — [ADR-0006](../docs/architecture/adr/0006-authentication-and-session-strategy.md) specifically calls out Service Key secrets as high-entropy/randomly-generated, so bcrypt's deliberate slowness would only cost the future high-volume Evaluation API latency for no security benefit). Returned in full exactly once, in `Create`'s response only (`createServiceKeyResponse` embeds `serviceKeyResponse` plus a `secret` field no other response has); every other response carries metadata only.
- **Environment scope**: `environment_ids` is a required array on Create (at least one) and an optional replace-the-whole-set array on Update (present-but-empty is rejected, same 0004 rule) — validated id-by-id against `EnvironmentRepository.GetByID` before writing, the same pre-check-then-write pattern `UserAccessService.ReplaceProfiles` uses for profile ids, so a bad id fails as a clean 400 instead of a raw FK-violation error out of `service_key_environments`.
- **Design note for future phases**: `ServiceKeyService.Get`/`List`/`Update`/`Deactivate` all fetch and return a key's environment ids *inside the service call itself* (a second query against `ServiceKeyEnvironmentRepository`, folded in before returning), rather than making the handler call two separate service methods. First-draft handlers that did call two separate methods (`Get` the key, then a second `EnvironmentIDs` call) dropped total coverage to 97.5% — each of those extra handler-level error branches ("first DB call succeeds, second one fails") is only reachable with a fault-injecting driver double, and doing that in five different handler methods was too many uncovered branches for the documented-exception pattern to still make sense (that pattern is meant for rare, isolated cases — see `internal/database/database.go`'s `Open`, or `EnvironmentRepository.List`'s count-then-page query, one each). Folding the second query into the service method itself moved that branch into the service test suite, where it's trivially mock-covered (no real DB, no fault injection needed) — restoring 100% handler coverage. Worth remembering for Phase 5+: if a handler needs data from two repository calls, do the combining in the service, not the handler.
- **Not built yet** (out of scope for this phase, per 0004's own Overview): service keys aren't usable as authentication yet — the `Authorization: Bearer <secret>` middleware that validates them against `can_read`/`can_write`/environment scope/`Active` status belongs to [0007-feature-flag-evaluation-api.md](../docs/business/requirements/0007-feature-flag-evaluation-api.md) (Phase 7). `model.ServiceKey.IsActive()` was deliberately *not* added yet either — nothing calls it until that middleware exists; add it then, not now.

### Killswitch & Notification Channels (Phase 6) — backend implemented, no frontend, not yet coverage-clean

Requirement [0006](../docs/business/requirements/0006-feature-flag-killswitch.md). Discovered already implemented and compiling when this file was audited on 2026-08-19 — **no prior session note recorded building it**, so the exact implementation date is unknown; treat the coverage/verification numbers below as this session's findings, not a fresh from-scratch build.

- **Notification channels CRUD** (`internal/service/notification_channel_service.go`, `internal/api/handler/notification_channel.go`): `POST/GET /api/v1/feature-flags/:id/notification-channels`, `PATCH/DELETE /api/v1/feature-flags/:id/notification-channels/:channelId`, all gated by `FeatureFlag: Edit` except `List` (`FeatureFlag: View`, per the usual CRUD-implies-View rule) — there's no separate permission surface for channels, per 0006. HTTP channels get a server-generated HMAC signing secret, AES-256-GCM-encrypted at rest ([ADR-0010](../docs/architecture/adr/0010-application-configuration-and-secrets.md)) and — unlike a Service Key secret — decrypted and returned on every read, not just Create, since the receiving system needs it to verify signatures ([ADR-0009](../docs/architecture/adr/0009-kafka-and-webhook-notification-delivery.md)).
- **Killswitch trigger** (`internal/service/killswitch_service.go`, `internal/api/handler/killswitch.go`): `POST /api/v1/feature-flags/:id/values/:environmentId/killswitch`, gated by the same `FeatureFlagValue: Write` permission as any other value change. Reuses `FeatureFlagValueService.Upsert` to flip `enabled = false` for that one environment, writes an `audit_log` entry (`AuditActionKillswitchTriggered`), then enqueues one `notification_outbox` row per enabled channel on the flag. The three writes are **not** wrapped in one DB transaction (no cross-repository transaction seam exists yet) — documented as an accepted gap in the service's own doc comment, not an oversight.
- **Not built**: no frontend at all for either sub-resource (no channel-management UI, no killswitch button) — nothing under `src/features/` references either. Also not built: the outbox *delivery* worker (actual Kafka publish / HTTP POST with HMAC signature, retries) — `notification_outbox` rows are written but nothing drains them; that's [ADR-0009](../docs/architecture/adr/0009-kafka-and-webhook-notification-delivery.md)'s worker, likely folded into Phase 9.

Not yet verified against a live running server (no `curl` smoke-test session note exists for this phase, unlike every other phase above).

**Frontend (`flgr-web-client`)** — Vite + React shell, Redux store, plus working feature slices: **first-run setup wizard** (`src/features/setup/`), **login** (`src/features/auth/`), **environments** (`src/features/environments/`), **feature flags** (`src/features/feature-flags/`, see Phase 5 section above), and — built 2026-08-19 via the multi-agent pipeline, backend was already done — **service keys** (`src/features/service-keys/`: list, create/edit form, one-time secret-reveal dialog, deactivate/reactivate). `RootGuard` (`src/app/RootGuard.tsx`) checks `GET /api/v1/setup` on every route under `/` and redirects to `/setup` when no User exists; `/setup` redirects back to `/` once it isn't needed (including reacting to a 409 if a race loses). `RequireAuth` gates everything else behind a valid session, redirecting to `/login`. `next-themes` now wired up too (`ThemeProvider` in `App.tsx`, `ThemeToggle` in `AppLayout` and the setup wizard) — light/dark, persisted to `localStorage["flgr-theme"]`, no flash on load (inline script in `index.html`). shadcn/ui components generated into `src/components/ui/` per ADR-0008. snake_case↔camelCase conversion at the RTK Query boundary (`src/lib/casing.ts`), per ADR-0007, reused by every `features/*/api.ts`.
